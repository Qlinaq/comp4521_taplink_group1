# TapLink feature status: F01–F28

This handoff maps the [proposal requirements JSON][requirements] to the implemented workflows. The last column distinguishes executed checks from remaining device coverage. Build identity, logs and limits are recorded in [VERIFICATION.md](VERIFICATION.md).

The current source provides workflows for 19 requirements. **F13 merchant QR entry is omitted.** F19 and F20 were added after the wallet was verified and are documented in [AUTH_DESIGN.md](AUTH_DESIGN.md). F21–F25 were added afterwards as a public-service/accessibility round (notifications, contact channels, accessibility and elderly mode, swipeable home cards, AI text support) and are documented in [ACCESSIBILITY.md](ACCESSIBILITY.md). F26–F27 answer two defects reported on a real device: a wallet that did not change when another account signed in, and Chinese text that could not be typed into the support field. F28 is a presentation round: one heading system for the four tab roots and a readable ring chart. All money, merchants, passes, rewards, subsidies, and service locations are demonstration data. There is no banking backend, real payment processing, NFC card integration, or official transport entitlement.

Use the [repository contract][contract] for data/domain integration and [PLATFORM_API.md][platform-api] for Android hooks, permissions, dependency/manifest snippets, cancellation, and lifecycle rules. Scenario IDs below refer to [TEST_PLAN.md][test-plan]; they identify checks to perform, not passed tests.

## Extension directions for teammates

- **Start at a concrete boundary.** UI and navigation live in `ui/` and `MainActivity`; domain types/rules and `TapLinkRepository` define the app contract; Room implementation owns persistence; `platform/` owns Android behavior. Follow [TEAM_HANDOFF.md][team-handoff] and keep the contract and this feature map aligned with accepted changes.
- **Keep financial changes in one repository transaction.** Extend operation types, validation, immutable records, receipt reconstruction, and idempotency together. Do not mutate balances directly from Compose, a worker, sensor, QR callback, or widget. Add a Room migration and exported schema when stored structures change; avoid destructive migration as a shortcut.
- **Add QR as data entry only.** Choose/document a small versioned payload, validate merchant IDs and positive integer-cent amounts against current data, handle malformed/unsupported codes, and expose a permission-aware scanner through `PlatformActions.scanMerchant`. Populate the existing form, then retain Review → Confirm and a stable operation ID. Test denial/cancellation and manual entry; decoding must never commit payment.
- **Grow discovery without overstating it.** Keep manual district mode and honest demo labels. A future map/data provider needs a documented source, freshness/error behavior, licensing and key management; the current app needs no map key. Keep asynchronous cancellation and coarse-permission support. Reuse the external `geo:` intent as a fallback.
- **Extend reminders deliberately.** Add new message types and eligibility rules together with preference controls and dedup tests. Preserve unique work names/policies unless a migration is planned. Exact alarms and push infrastructure are not present; adding a UI promise of exact delivery would require a separate design and validation. Catalogue refresh currently preserves existing records, so updating seeded content requires an explicit version/update policy.
- **Preserve independent privacy controls.** Any new widget layout or per-instance settings must still hide balance by default and refresh after committed changes. Dashboard visibility currently affects that card display only; broader privacy would need coordinated rules for review/receipts, messages, sharing, and widgets. Keep shake limited to visibility and lifecycle cleanup.
- **Record what was actually demonstrated.** Update the relevant row, acceptance scenario, and evidence after a change. Include failures, omitted scenarios, and device limitations. A passing JVM test, compiled APK, or simulated sensor sample should not be substituted for a real launcher/permission/sensor check.
